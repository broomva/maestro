Maestro in Rust: a typed governance metalayer over any harness

One typed model of the orchestration we learned on Paseo, exposed as a CLI and an MCP server, so any agent harness can read the fleet's governance state, get the right context injected, and later act through owner-verified verbs.

The four questions Maestro answers

  1. What is happening? Work states, loops and their last tick, and the fleet census.
  2. What changed? Tick receipts, and answers waiting to land.
  3. What evidence exists? Every section names its source and its read errors.
  4. What do you need from me? Needs: only concrete holds on the owner.

Position

Three Maestros came before this one. Each left lessons, and this project types them:

  • broomva/maestro-legacy is the TypeScript app, chat-first, with work as folders and the gate as the human's verb. It was archived on 2026-10-18.
  • broomva/maestro-paseo is the live Paseo plugin. It holds the work store, owner verbs with an 8 second undo, answer landing and routing, the wake loop, and the fleet and loops readers.
  • The T3 MCP proof of concept is a TypeScript stdio server with three tools and a 1.3k-line web app. It answered asks from a second process, outside the owner path, and the BRO-3186 contract names that as the defect to avoid.

The new Maestro is harness-agnostic. Harnesses are adapters: T3 Code, Claude Code, Codex, Paseo and Gemini. The substrate stays where it is. The fleet skill does census and agent mail, bstack does hooks and gates, and .control/ and .broomva/loops/ hold the truth. Maestro types that substrate, reads it, derives shared views, and injects context. Orchestrator sessions drive the work, with Maestro as their governance surface.

Data model

Field names follow the on-disk contracts verbatim. Enums that are open-ended on disk carry an Other arm, so an unknown value is reported, never dropped. Every record keeps unknown keys in extra, so nothing Maestro rewrites later can lose a field.

Canonical work states

Queued Running Stuck Needs you Done Standing

The mapping is the plugin's PLAIN_VOICE. Stored proposed, reviewing and triggered map to Queued. Running maps to Running, or to Standing when the last event is a quiet flag. Blocked maps to Stuck, and review to Needs you, marked finished when no hold exists. Done and canceled map to Done. Counts are reported by stored state; only the needs list is the Needs you count.

Authority

Reads

Scoped observations for coordinators and dashboards. Any caller can read. This is every tool in phase 0.

Agent requests

File a validated ask, queue owner-gated work, or request one exact held action. These need a session whose identity was checked against its host's registry.

Owner actions

The verbs are ask.answer, approval.decide, work.verdict, work.dispatch, verb.undo, fleet.review, conductor.decide and initiatives.review. They need a verified owner principal and have an 8 second undo.

A model-visible tool is never proof of the owner, and a client-supplied actor: human is not a principal. Principal::Unverified may only read. A test fails if any owner verb becomes reachable through MCP.

Context injection

A context packet is built from one snapshot and scoped to the session. Maestro infers the project from the cwd (core/maestro gives maestro). It infers the initiative from links.repos or a matching id. The packet carries the session's holds, the open asks in its scope (so it does not re-ask them), its initiative's next action, loops needing attention, unread sources and the standing rules. Only the envelope changes per harness.

Governor and ticks

A tick is one bounded fire of a standing loop. It opens with loop.tick.started and works its due tiers within a call budget. It then writes its state file atomically and closes with loop.tick.ended, caused by the start. Maestro types this lifecycle today and reports its drift. In phase 3 it becomes the governor: for each scope, one orchestrator session owns the tick. Maestro picks that session's host by capability, not by name, and injects its context. Maestro verifies the receipts and does not run the work itself.

Phases

Phase 0: typed reads everywhere (this change)

Cargo workspace with core, store, MCP and CLI. Nine read tools, a context prompt and three resources. The hook format never fails a session, whether it gets a bad argument or overruns its 5 second budget. Git reads resolve one commit per store and use ls-tree -z. Unlanded answers are detected. 47 tests run against a fixture machine, with golden values from the plugin's own functions, and 9 guards were checked by mutation. The binary is installed at ~/.local/bin/maestro, and both POC registrations (Claude Code local, Codex) now point to it.

Phase 1: agent requests

File an ask through ask_ledger.py validation and the shared lock protocol (~/.local/state/control-asks/locks). Queue owner-gated work. Check host identity for T3 and Paseo callers. Read live work holds from host adapters, so permission prompts become needs.

Phase 2: owner path

An authenticated owner principal: a local signed token or a verified host confirmation. Owner verbs get receipts, appliesAt and an 8 second undo. Answer landing and routing move to Maestro, and the plugin's writer retires in the same change, so there is always one writer.

Phase 3: governor over host adapters

Launch, send, interrupt, archive and schedule adapters for T3, Paseo and Claude Code. Each scope has exclusive ownership recorded in the loop registry. Thread-message context injection and lifecycle ingestion. A T3 schedule substrate with busy, restart and duplicate-delivery tests.

Phase 4: owner surface

An MCP App view built on the Broomva agentic-work profile (RunCard, WorkState, Receipt) from the same snapshot. Its sections are Feed, Decisions, Work, Health and Initiatives. Mobile state survives in the backend.
