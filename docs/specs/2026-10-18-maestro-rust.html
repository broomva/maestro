Maestro in Rust: a typed governance metalayer over any harness

One typed model of the orchestration we learned on Paseo, exposed as a CLI, an MCP server and an HTTP daemon, so any agent harness can read the fleet's governance state, file requests, and let the owner act through verified verbs. Rev 2 turns the phase list into the contract every build node of the production plan works from.

Objective

Replace the Paseo plugin as the governance runtime with a typed, harness-agnostic Maestro, without ever having two writers, or none, for a ledger. The plugin keeps rendering for the owner on Paseo; Maestro becomes the only author of ask answers, work, verbs and loop state, and the owner reaches all of it from any harness and from the iPhone.

Goals

  1. Any harness. Claude Code, Codex, Gemini, T3 and Paseo read the same snapshot and file the same requests, through MCP (stdio or HTTP) or the CLI.
  2. One writer per ledger, at every step. Each ledger family moves from the plugin to Maestro in one release, behind a lease that refuses a second writer.
  3. The owner, verified. Owner verbs need a verified owner principal, keep the 8 second undo and re-check what they act on when they apply.
  4. No Mac-only step. With the Mac asleep, the owner reads needs, answers asks and reviews initiatives through the always-on node.
  5. Parity before replacement. Every predicate, verb and writer ported from the plugin is proven by golden parity: the plugin's own code under bun and the Rust port on the same scenarios.

Non-goals

  • Retiring the Paseo plugin's UI. A reader would expect a rewrite to delete the old app. It stays: the owner uses its desktop and phone screens daily, and after cut-over 3 it renders from maestrod and writes nothing. Deleting it would remove the only surface the owner has until the MCP App and iOS app reach parity.
  • Automatic lease failover or consensus. One writer per ledger invites Raft. The lease moves by an explicit maestro lease move (owner or runbook), because the fleet is two to three machines, the always-on node has been the stable one, and a consensus layer would be the largest component in the system for a failure the runbook covers in minutes.
  • Moving the ledgers into Lago's journal. The fleet ADR rejected it: .control/asks, .control/initiatives and .broomva/loops stay files in the workspace tree; only who authors them changes. Phase 0 reached 234/234 parity reading them in place.
  • Cross-node live session migration. Work moves by publishing a branch and starting a session elsewhere; a running session stays on its node (fleet ADR non-goal).
  • The full YAML 1.2 port (BRO-3224). Maestro writes only YAML inside its subset, and a round-trip test enforces that; the three subset gaps are documented (BRO-3229, node hygiene).
  • Editing owner-only files. .control/policy.yaml and .control/preauth.yaml change only through owner-applied, owner-signed diffs. Maestro drafts the enforcement diff as an ask (node enforce-ask) and never writes it.
  • The change plane (Cuenca, BRO-3231). It has its own loop and plan; the coupling is the shared core/identity crate and the rmcp version.

Context: what exists

Three Maestros came before this one: broomva/maestro-legacy (TypeScript, archived 2026-10-18), the T3 MCP proof of concept (answered asks from a second process, the defect the BRO-3186 contract names), and broomva/maestro-paseo, the live Paseo plugin. The plugin is about 50k lines of TypeScript and is today's writer: the work store, the 13 owner verbs of shared/verbs.ts plus the immediate work verbs, answer landing and routing, the wake loop, and every screen the owner uses on the Mac and the iPhone. Inventory read at plugin origin/main e07581a on 2026-10-21.

Phase 0 shipped (maestro#1, #3, c60620a): four crates, nine read tools, a context hook, parity with the plugin on all real asks, and a required ci check (node ci, maestro#4). It is installed at ~/.local/bin/maestro and registered in Claude Code, Codex and Gemini. The fleet ADR (workspace:docs/adrs/2026-10-19-fleet-runtime-boundaries.html, accepted) fixes the boundary this spec builds inside: three planes with one author each, the core/identity crate, placement by Maestro alone, owner-signed hooks, and one home per kind of data. This spec does not redefine Principal, SessionRef, Node, Surface or Harness; it cites the ADR.

Design

Harnesses are adapters. The substrate stays where it is: the fleet skill does census and agent mail, bstack does hooks and gates, and .control/ (or .broomva/, by the path registry) and ~/.broomva/ hold the truth. Maestro types that substrate, reads it, derives shared views, injects context, and, from phase 2, is the one writer of the ledgers the plugin writes today. Orchestrator sessions drive work; Maestro is their governance surface and, from phase 3, their governor.

Crates after phase 0.5

Short directories, package names kept short (node split): crates/core, crates/store, crates/mcp, crates/cli (package maestro), then crates/hosts (phase 1), crates/view (phase 1), crates/auth and crates/ledger (phase 2), crates/governor (phase 3), and apple/ (phase 5). The shared identity types live outside, in broomva/identity at core/identity, consumed as a tagged git dependency, never a path dependency, so hosted CI builds without credentials.

Topology

maestrod is maestro serve --http run as a service. It runs on every machine of the fleet and is stateless per request: each request builds a fresh Store and resolves origin/main again, so two daemons never disagree for longer than one fetch. What is not stateless is the writer: for each ledger family exactly one daemon holds the lease, and a write that arrives at another daemon is forwarded to the holder over the tailnet.

Decision: the writer lease lives on the always-on node

The production plan left this to rev 2. Taken: each family's lease lives on the always-on node from the later of deploy (phase 4) and the family's own cut-over. deploy moves the leases of the families Maestro writes at that time (at least asks: the graph orders it after cutover-asks); a family cut over after deploy takes its lease on the always-on node directly. Before deploy the Mac runs Maestro's only daemon, so any lease Maestro holds is there; a family not yet cut over has no lease, and the plugin writes it on the Mac. The evidence: the Mac's power log for 2026-10-18 shows 26 sleep entries against 2 full wakes (the rest are dark wakes: brief maintenance wakes with the display off, not a window the owner can count on), so a Mac-held lease would make every answer from the iPhone wait on the Mac waking. The exit clause "no Mac-only step" is defined concretely as: with the Mac asleep, the owner reads needs, answers an ask and reviews an initiative, and each lands through the gates; no write waits on the Mac. Effects on Mac sessions (a prompt, an Allow) are deliveries, queued with a delivery key and applied once when the Mac's daemon is reachable; the verb itself is recorded and its undo window closes on the always-on node.

The trade-off: the always-on node becomes the place where a fault stops writes. It costs a manual lease move when the node is lost (the runbook's drill, node runbook), and it gives up the Mac's local-disk latency for writes from Mac sessions, a tailnet round trip (79 ms from the Mac to the VPS by tailscale ping, 2026-10-21), against the 5 second hook budget.

Other topology rules

  • Bind: loopback by default; a tailnet address only when named with --bind; never 0.0.0.0 (node http tests it).
  • OS user: _maestro (LaunchDaemon) on macOS, maestro (systemd) on Linux. Maestro's signing key is readable only by that user; agents run as the owner's user and cannot read it (fleet ADR, section 2).
  • Host adapters run where the sessions run: a daemon only launches, prompts or interrupts sessions on its own node.
  • Registrations: every harness on every machine points at the tailnet HTTP endpoint from phase 4, with maestro mcp over stdio kept as the fallback.

Authority

Reads

Any caller. Every tool in phase 0.

Agent requests

ask.file, work.queue (always held), action.request, session.close --receipt, handback, escalate. Need a session verified against its surface's registry; an unverified caller's request is recorded and held.

Owner actions

The owner verbs. Need a verified owner principal: a passkey assertion bound to the verb and its content hash. 8 second undo and a re-check at apply.

A model-visible tool is never proof of the owner, and a client-supplied actor: human is not a principal. Principal::Unverified may only read. crates/mcp/tests/authority.rs enumerates every tool and fails if one maps to an owner verb.

Decision: the owner principal is a passkey, verified by maestrod

maestrod serves a passkey page at a tailnet HTTPS name. The MCP App opens it with open-link (Face ID cannot run inside the sandboxed ui:// iframe); a verified assertion yields an owner token bound to one verb and the hash of its content, valid for that verb only. The owner certifies Maestro's signing key once, with the Secure Enclave key of the fleet ADR, and rotates it quarterly. Reversal cost: one-way door. Every owner verb, the iOS app's key and the dogfood receipts rest on it, and a forged owner verb loosens every gate at once, so node auth runs at frontier tier with a forgery suite that must hold 0 of 10.

Owner verbs

Ported exactly from the plugin, names unchanged. The queue semantics come from server/owner-verbs.ts: a verb is recorded as verb.pending with appliesAt = call + UNDO_MS (8000, shared/undo.ts; a shorter window is honoured only under test, never by a daemon); verb.undo takes it back while the window runs; when the window closes the applier writes verb.claimed with its pid and start, re-runs the verb's guard, and settles it as verb.applied, or verb.dropped with the reason when what it acted on moved. A second pending verb with the same name and key is refused with ALREADY_PENDING, unless the verb supersedes: then the older one is undone ("Replaced by a newer one"), except one taking effect that moment, which applies while the newer waits its own window. Different verbs on one key may be pending together. A due verb that needs a surface client and finds none stays pending, unclaimed, and is re-armed to retry. On start, the sweep applies every overdue verb and arms the rest, so a restart inside the window still applies it; a claim by a live process is left to it, and a claim by a dead process settles as dropped, because a second prompt is worse than none. Every write is under the ledger's file lock. Golden parity: the plugin's own queue under bun and the Rust queue write the same line kinds and outcomes on shared scenarios (node ledger-writer).

Plugin retirement

One row per ledger the plugin writes, and per class of effect it has on live sessions, from the inventory at plugin e07581a. The cut-over rule: the plugin stops writing a family in the same release Maestro starts. The release notes name both SHAs; the plugin's startup check refuses to write a family whose lease maestrod holds; a grep-and-spy test (every write primitive: writeFileAtomic, appendJsonLine(s), appendLinesLocked, writeFile, rename, git and gh calls, Paseo agent writes) proves no plugin path writes a retired row; rollback is one flag that returns writing to the plugin, accepted only once maestrod has released the lease. Lock directories (~/.local/state/control-asks/locks, each store's .locks) are a shared protocol, not a ledger: Maestro joins them in node agent-requests and both sides keep using them.

Decision: config.json is governance, not surface settings

The plan and the cut-over tickets called config.json, the wake log and the inbox file "surface settings" that stay with the plugin. Reading the schema says otherwise: every key of ConfigSchema governs work (where it runs, the cap, the default gate, the wake cadence), and the wake log and inbox file are the wake loop's and the notifier's own state. Leaving them with the plugin would leave a second writer for state maestrod acts on. So R15 moves at cut-over 2 and R17, R18 at cut-over 3; after cut-over 3 the plugin writes nothing but client-side UI state in the browser (tabs, drafts, theme). Reversal cost: two-way door; the keys are few and the move is a file copy.

Governor and ticks

A tick is one bounded fire of a standing loop: loop.tick.started, its due tiers within a call budget, an atomic state write, and loop.tick.ended caused by the start. In phase 3 Maestro becomes the governor: for each scope exactly one orchestrator session owns the tick, recorded as exclusive ownership in the loop registry. Maestro places that session by capability (node, harness, surface, subscription, model, effort; fleet ADR section 3), within per-node runner budgets it sets and the economy mode from node port, injects its context, and verifies its receipts: a loop registered with a receipts contract that writes none is drift within twice its cadence (BRO-3189). Maestro does not run the work itself. A harness whose hooks fail their canary receives no new session, and under the owner's standing rule of 2026-10-19 its running sessions are interrupted after a 2 minute grace and a need is raised. A8 holds: the governor dispatches only on an owner verb or a standing grant in .control/preauth.yaml.

Alternatives considered

How the plugin's writer retires

  • One big cut-over after Maestro reaches full parity. Fewer releases, one rollback. Rejected: the plugin writes the 19 rows of the retirement table from about 50k lines, so a single switch would land every risk at once, and the owner would lose answering for as long as any one family is broken.
  • Dual write with reconciliation during a transition (both write, a job reconciles). The usual migration pattern, and it keeps rollback trivial. Rejected against our own goal: two writers for a ledger is the defect the BRO-3186 contract forbids, and several rows cannot be reconciled after the fact (a git branch with a pushed batch PR, a prompt already delivered to a session), so reconciliation would need a merge rule per row that the plugin never had.
  • Chosen: per family, in the same release, behind a lease, asks then work then loops. It gives up speed: three plugin releases, each with a grep-and-spy test and a rollback flag.

Where the writer lease lives

  • On the Mac, where the sessions are. Lowest latency for agents filing asks, nothing new to operate. Rejected: the exit's "no Mac-only step" fails whenever the Mac sleeps, which its power log shows is most of the time (26 sleeps against 2 full wakes on 2026-10-18).
  • Split per family: asks on the always-on node, work and loops on the Mac. Plausible, since work effects need the Mac's sessions anyway. Rejected: two homes for Maestro's state, and an owner verdict recorded while the Mac sleeps would fail instead of queueing.
  • Chosen: each family on the always-on node from the later of deploy and its cut-over, effects on Mac sessions queued as idempotent deliveries.

The owner principal

  • A local signed token file. Simplest. Rejected: agents run as the owner's user and can read it.
  • The surface's own confirmation (Paseo's UI as proof). Works today. Rejected as the mechanism: it binds the owner to one surface, against "from any harness".
  • The owner's Secure Enclave SSH key (Secretive, Touch ID), the key the fleet ADR chose for signed policy commits (BRO-3210). Strong. Rejected for verbs: it lives on the Mac, so answering from the iPhone would be a Mac-only step; it stays the key that certifies Maestro's key.
  • Chosen: a passkey verified by maestrod, which works on the iPhone and the Mac and binds one verb and hash.

Transport

  • stdio only, one process per harness session. What phase 0 ships. Rejected as the end state: no cross-machine reach, so the iPhone and the always-on node cannot use it. Kept as the fallback.
  • A Unix socket daemon. Peer credentials for free. Rejected: machine-local, so again no iPhone. Kept for the owner CLI and the agent socket.
  • Chosen: stateless Streamable HTTP (rmcp 3.x), bound to loopback and the tailnet.

Where Maestro's own records live

  • SQLite. Transactions and queries. Rejected: the plugin's records are JSONL with hash chains that the parity tests and broomva_home.py already read, and SQLite would add a migration and a second format with no reader that needs it.
  • Chosen: a hash-chained JSONL event stream, the format the tick ledger already uses, as the record; work folders stay as its projection in the plugin's format, at the cost of a second write per work mutation, so Paseo's readers need no change.

Drawbacks

  • Cost: a new secret and a new service. Maestro's signing key needs its own OS user, backups of encrypted key material, and quarterly rotation; a lost key is a runbook procedure and an owner certification.
  • Cost: the always-on node is the write path. Losing it stops writes until someone runs maestro lease move; we accept a manual failover over a consensus layer.
  • Cost: three plugin releases. Each cut-over is a frontier-tier review with a 24 h window of risk; rolling one back needs maestrod to release its lease first.
  • Cost: every agent ask now waits on Maestro being up. An ask filed while Maestro is unreachable queues in the node's outbox (fleet ADR); agents can no longer hand-edit ledgers.
  • Cost: two renderers. The MCP App and the iOS app must both follow catalog v1; any v2 change ships twice.

Open questions

  • Which API T3 exposes to a process outside MCP for thread identity, launch and send. Next step: node host-identity researches it and records the source here; if T3 has none, the T3 adapter runs inside a T3-hosted orchestrator session.
  • When the iOS app ships relative to a week of the MCP App in daily use. Next step: the owner decides at node ios; the graph follows the 2026-10-19 decision (after the MCP App).
  • Whether to apply enforcement of Maestro-authored paths or stay log-only. Next step: the owner answers enforce-maestro-authored; the dogfood receipt records either answer.
